# A8 Config ACK: Technical Contract

Status: implemented. This is the current technical reference for the A8 configuration acknowledgement flow. Historical contracts that describe the earlier `PUBLISHED` response are superseded by this document.

## 1. Purpose

HTTP `202 Accepted` and a successful Backend MQTT publish only show that the Backend accepted and published a configuration request. They do not prove that the ESP32 validated, persisted, or applied it. A8 adds an end-to-end acknowledgement correlated by `configId` so the Backend and Dashboard can report the device result.

## 2. Message flow

```text
Dashboard
  -> POST /api/config
Backend
  -> greenhouse/01/config
ESP32
  -> validate candidate thresholds
  -> persist changed thresholds to NVS
  -> apply thresholds and requested mode
  -> greenhouse/01/config/ack
Backend
  -> REST status + WebSocket config_result
Dashboard
```

## 3. MQTT configuration request

| Property | Value |
|---|---|
| Topic | `greenhouse/01/config` |
| Direction | Backend to ESP32 |
| QoS | 1 |
| Retain | false |

Payload keys use camelCase:

```json
{
  "configId": "cfg-e710c4cf3956",
  "mode": "AUTO",
  "tempOnC": 36,
  "tempOffC": 33,
  "humidityOnPct": 50,
  "humidityOffPct": 70,
  "lightOnLux": 270,
  "lightOffLux": 730
}
```

`mode` is `AUTO` or `MANUAL`. Threshold pairs are temperature in °C, humidity in percent, and light in lux. The Backend validates the threshold ranges and hysteresis before publishing; the firmware validates the candidate again before applying it. `configId` is generated by the Backend and is limited to 64 characters by the firmware.

## 4. MQTT acknowledgement

| Property | Value |
|---|---|
| Topic | `greenhouse/01/config/ack` |
| Direction | ESP32 to Backend |
| QoS | 1 |
| Retain | false |

Example successful acknowledgement:

```json
{
  "deviceId": "greenhouse-01",
  "configId": "cfg-e710c4cf3956",
  "result": "APPLIED",
  "reason": null
}
```

`result` is `APPLIED` or `REJECTED`. The firmware currently emits these rejection reasons:

- `INVALID_MODE`
- `INVALID_NUMBERS`
- `INVALID_THRESHOLDS`
- `NVS_WRITE_FAILED`

An invalid JSON payload or missing, empty, or overlength `configId` is logged and ignored because it cannot be correlated; no ACK is sent. Successful ACKs use a null reason.

## 5. Backend ACK lifecycle

The Backend tracks each request through:

```text
PENDING -> APPLIED
PENDING -> REJECTED
PENDING -> TIMEOUT -> APPLIED (wasLate=true)
PENDING -> TIMEOUT -> REJECTED (wasLate=true)
```

`TIMEOUT` means the Backend did not receive a valid ACK before its configured deadline; it does not prove the device failed to apply the request. A later valid ACK replaces the timeout result and is marked `wasLate=true`. The Backend broadcasts the timeout transition and the later terminal result as separate WebSocket events.

Unknown `configId` values and ACKs with an unsupported result are logged and ignored. After an `APPLIED` or `REJECTED` result, a duplicate QoS 1 ACK is ignored and does not cause another WebSocket push. A valid ACK received after `TIMEOUT` is accepted once; subsequent terminal duplicates are ignored.

The ACK `deviceId` is required and must match the device registered for that `configId` when the request became `PENDING`. A missing or mismatched device identity is logged and ignored: it does not change the lifecycle, cancel the timeout, or produce a WebSocket event. Terminal records and WebSocket destinations retain the registered device identity.

## 6. REST API

`GET /api/config?deviceId=greenhouse-01` returns the latest desired configuration stored by the Backend. That record is not a device-application acknowledgement.

`POST /api/config?deviceId=greenhouse-01` accepts a configuration body containing `mode`, `tempOnC`, `tempOffC`, `humidityOnPct`, `humidityOffPct`, `lightOnLux`, and `lightOffLux`. `deviceId` defaults to the configured device when omitted. On successful MQTT publication it returns HTTP `202`:

```json
{
  "configId": "cfg-e710c4cf3956",
  "status": "PENDING",
  "config": {
    "mode": "AUTO",
    "tempOnC": 36,
    "tempOffC": 33,
    "humidityOnPct": 50,
    "humidityOffPct": 70,
    "lightOnLux": 270,
    "lightOffLux": 730
  }
}
```

The `202` response means the request was published and is awaiting device acknowledgement. Validation failures return `400`; an offline device returns `409`; a failed MQTT publish returns `503`.

`GET /api/config/status?configId=cfg-e710c4cf3956` returns the lifecycle record:

```json
{
  "configId": "cfg-e710c4cf3956",
  "deviceId": "greenhouse-01",
  "status": "APPLIED",
  "reason": null,
  "wasLate": false
}
```

The status is one of `PENDING`, `APPLIED`, `REJECTED`, or `TIMEOUT`. An unknown `configId` returns `404`. Records are held in memory and are lost when the Backend restarts.

## 7. WebSocket contract

The Backend sends `config_result` only for terminal lifecycle transitions: `APPLIED`, `REJECTED`, and `TIMEOUT`. It does not broadcast `PENDING`.

```json
{
  "type": "config_result",
  "data": {
    "configId": "cfg-e710c4cf3956",
    "result": "APPLIED",
    "reason": null,
    "wasLate": false
  }
}
```

`result` uses the terminal state name, including `TIMEOUT`. A later ACK after timeout produces a second event with `APPLIED` or `REJECTED` and `wasLate: true`.

## 8. Firmware validation and persistence

The firmware builds a candidate from the request and validates its mode, numeric values, ranges, and hysteresis before changing live values. If threshold values changed, it writes the candidate threshold blob to ESP32 Preferences/NVS first. A failed write returns `REJECTED` with `NVS_WRITE_FAILED` and leaves the current thresholds, mode, and actuator outputs unchanged. After a successful write (or when threshold values did not change), it updates the live thresholds and requested mode, then publishes `APPLIED`.

Stored thresholds are loaded at boot and survive an ESP32 software reset. If the stored blob is absent, has the wrong size, or fails validation, firmware keeps its compiled defaults: 30/28 °C, 55/65%, and 300/700 lux. The mode is not persisted by this A8 threshold-storage path. A fresh Wokwi simulation may start with empty NVS; this is separate from an ESP32 software reset.

## 9. Duplicate delivery semantics

MQTT QoS 1 is at-least-once and may redeliver a request or ACK. During one boot, firmware caches the result for only the most recently handled `configId`; a matching duplicate resends that cached ACK without repeating the configuration side effects. The cache is volatile and is lost on reboot. This is bounded duplicate protection, not durable or global exactly-once processing; an older ID that is no longer the cached ID can be handled again.

Backend terminal ACK handling is idempotent for duplicate `APPLIED`/`REJECTED` messages and prevents duplicate WebSocket pushes for that terminal result.

## 10. Dashboard behavior

- Shows `PENDING`, `APPLIED`, `REJECTED`, and `TIMEOUT`, including the config ID and rejection reason.
- Uses WebSocket `config_result` for realtime updates and polls `GET /api/config/status` while a request remains pending.
- Buffers a result that arrives over WebSocket before the POST response establishes the active `configId`.
- Ignores results and polling responses for stale config IDs so an older request cannot replace the current result.
- Displays a later ACK after timeout as a late result.
- Blocks another configuration publish while the active request is `PENDING`.

## 11. Timeout setting

`CONFIG_ACK_TIMEOUT_S` controls the Backend ACK deadline. Its default is `5` seconds. The timeout is Backend-side and does not cancel a configuration already delivered to the device.

## 13. Known limitations

- Backend ACK lifecycle records and timeout tasks are in memory and do not survive a Backend restart. A status lookup after restart may return `404` for a prior request.
- The persisted `device_configs` row is the latest desired/requested configuration and its publication timestamp; it is not proof that the ESP32 applied it. The ACK lifecycle is the device-result source, but is not persisted.
- Firmware duplicate protection remembers only the latest config ID during the current boot.
- Firmware persists thresholds, not the requested mode. A fresh Wokwi simulation may also begin with empty NVS.
